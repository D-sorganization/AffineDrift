\chapter{Forward and Inverse Simulation}
\label{ch:simulation}

Forward dynamics predicts acceleration from a state and specified forces. Inverse
dynamics computes the generalized forces required by a specified motion, under
a specified model and external loading. Inverse kinematics instead solves for
configurations that realize a geometric task. These operations answer different
questions: an inverse-dynamic torque is not a unique explanation of the muscles
or intentions that produced an observed swing.

\section{Dynamics Evaluation Is Not Time Integration}

For a fixed-base rigid chain with minimal joint coordinates, write
\begin{equation}
 M(q)\ddot q+C(q,\dot q)\dot q+g(q)=\tau.
 \label{eq:simulation-rigid-dynamics}
\end{equation}
Here $M$ is the inertia matrix, $C\dot q$ the velocity-dependent generalized
force, and $g=\nabla_q U$ the gravitational term. The two algebraic operations are
\[
 \operatorname{FD}(q,\dot q,\tau)
   =\operatorname{solve}(M,\tau-C\dot q-g),\qquad
 \operatorname{ID}(q,\dot q,\ddot q)=M\ddot q+C\dot q+g.
\]
Solving the linear system avoids explicitly forming $M^{-1}$.

The recursive Newton--Euler algorithm (RNEA) evaluates inverse dynamics using
both a forward kinematic/acceleration pass and a backward wrench pass. They are
not alternative switches for forward versus inverse dynamics. One can construct
the bias and mass-matrix columns with repeated inverse-dynamics calls, then
solve for acceleration; the articulated-body algorithm (ABA) computes forward
dynamics directly. Neither RNEA nor ABA advances time. A separate integrator
uses the resulting vector field~\cite{Featherstone2008,LynchParkRNEAReview}.

\section{A Reproducible Rigid Golf-Chain Example}

The following listing runs from the repository root with Python 3.12, NumPy and
SciPy. It uses the same canonical uniform-rod model as the capstone
(Chapter~\ref{ch:golf-capstone}), rather than a second incompatible set of
pendulum equations. The three lengths are $(0.28,0.46,1.10)$ metres and masses
$(2.16,1.79,0.30)$ kilograms; these are teaching parameters, not measured subject
data. Each COM is halfway along its rod and $I_{\mathrm{COM}}=m\ell^2/12$.

The plane is $(x,y)$ with gravity along $-y$. The first angle is measured from
$+x$; the other two are relative angles. Thus a straight downward chain is
$q=(-\pi/2,0,0)$, whereas $q=0$ is horizontal. The state is
$(q_1,q_2,q_3,\dot q_1,\dot q_2,\dot q_3)$, with radians, seconds and newton-metres
as the angular, time and torque conventions. This fixed-base model has no
contact, joint limits, damping, muscle activation or shaft deformation. Its
generalized torque input is not an excitation signal.

\begin{lstlisting}[language=Python, caption={Forward and Inverse Dynamics of the Canonical Rigid Chain}]
from collections.abc import Callable

import numpy as np
from scipy.integrate import solve_ivp

from src.affine_control.swing_analysis import SwingAnalysis

RIGID_MODEL = SwingAnalysis().model()


def finite_vector(value: np.ndarray, size: int) -> np.ndarray:
    """Return a finite vector of the required physical dimension."""
    result = np.asarray(value, dtype=float)
    if result.shape != (size,) or not np.all(np.isfinite(result)):
        raise ValueError(f"Expected a finite vector of size {size}")
    return result


def dynamic_terms(state: np.ndarray) -> tuple[np.ndarray, np.ndarray]:
    """Return the inertia matrix and total gravity/velocity bias."""
    state = finite_vector(state, 6)
    position, velocity = state[:3], state[3:]
    mass = RIGID_MODEL.rigid_mass_matrix(position)
    bias = (RIGID_MODEL.coriolis(position, velocity) @ velocity
            + RIGID_MODEL.gravity_torque(position))
    return mass, bias


def inverse_dynamics(state: np.ndarray,
                     acceleration: np.ndarray) -> np.ndarray:
    """Return required generalized torque for this rigid model."""
    mass, bias = dynamic_terms(state)
    return mass @ finite_vector(acceleration, 3) + bias


def forward_dynamics(state: np.ndarray,
                     torque: np.ndarray) -> np.ndarray:
    """Return acceleration; reject unsupported state/torque shapes."""
    mass, bias = dynamic_terms(state)
    return np.linalg.solve(mass, finite_vector(torque, 3) - bias)


def simulate(initial: np.ndarray, times: np.ndarray,
             control: Callable[[float, np.ndarray], np.ndarray]
             ) -> dict[str, np.ndarray]:
    """Integrate a smooth torque law at requested output times."""
    initial = finite_vector(initial, 6)
    times = np.asarray(times, dtype=float)
    if (times.ndim != 1 or times.size < 2
            or not np.all(np.isfinite(times)) or times[0] != 0
            or np.any(np.diff(times) <= 0)):
        raise ValueError("Times must increase from zero")

    def derivative(time: float, state: np.ndarray) -> np.ndarray:
        """Evaluate continuous feedback at internal solver stages."""
        acceleration = forward_dynamics(state, control(time, state))
        return np.concatenate([state[3:], acceleration])

    result = solve_ivp(derivative, (0, times[-1]), initial,
                       t_eval=times, method="DOP853",
                       rtol=1e-8, atol=1e-10)
    if not result.success:
        raise RuntimeError("Forward integration failed")
    return {"time": result.t, "state": result.y.T}
\end{lstlisting}

For example, passing a callback that returns \texttt{np.zeros(3)} releases this
model with zero applied joint torque. The solver still includes gravity and
inertial coupling. Its adaptive internal steps differ from the requested output
times. The callback describes continuous feedback evaluated at intermediate
states; a sampled controller with held commands must instead specify its update
times and integrate separately across those discontinuities. Contact events
likewise require an event law and, where applicable, a velocity reset.

The canonical model obtains gravity and Christoffel terms using finite
differences with coordinate step $10^{-6}$ radians. Tightening an integrator's
tolerance cannot remove the derivative approximation error. The listing is an
explicit mass-matrix solve, not an implementation of RNEA or a benchmark of the
companion platform's engine adapters.
The method named \texttt{gravity\_torque} returns $\nabla U$, the holding-torque
term on the left of the dynamics equation, not the applied gravity force
$-\nabla U$.

\section{Verification Before Interpretation}

The identity $\operatorname{ID}(\operatorname{FD}(\tau))=\tau$ at a common
$(q,\dot q)$ checks algebra and conventions, but shared errors can cancel. Use
independent tests too: gravitational moments at a horizontal configuration,
equilibrium of the downward chain, positive inertia, and mechanical work balance.
For this model,
\[
 E=\tfrac12\dot q^T M(q)\dot q+U(q),\qquad
 E(t)-E(0)=\int_0^t\dot q^T\tau\,\mathrm dt.
\]
This follows from the Christoffel identity
$\dot M-2C$ skew-symmetric. It does not require $C$ itself to be skew-symmetric.
Energy residual and state/phase convergence should both be checked as numerical
settings change; energy agreement alone does not establish trajectory accuracy.

For measured golf motion the equation becomes, schematically,
$M\dot v+h=B\tau+J^T\lambda$. Ground and hand forces, passive tissues and actuator
dynamics must be allocated consistently. A floating base has unactuated
equations; an arbitrary kinematic recording need not admit a feasible solution.
Even when net joint torque is identified, many muscle-force combinations may
produce it. Differentiation noise, filtering and inertia uncertainty propagate
directly into that estimate. Forward replay under the inferred input tests
consistency; independent measurements test the physical model.

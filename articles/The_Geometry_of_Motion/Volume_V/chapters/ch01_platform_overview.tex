\chapter{The Companion Platform}
\label{ch:platform}

A simulation platform makes a modeling argument executable: which bodies move,
which forces act, what the controller observes, and what an experiment measures.
A common method name cannot by itself guarantee common physics. This chapter
establishes contracts for turning the geometric and biological arguments of
earlier volumes into a reproducible calculation. Its executable example is a
simple pendulum, not a validated human swing or a demonstration of every adapter.

\section{Architecture and Capability Boundaries}

UpstreamDrift contains engine wrappers and shared Python interfaces. At the
inspected revision, common interfaces live under
\texttt{src/shared/python/engine\_core/}, with engine implementations under
\texttt{src/engines/physics\_engines/}. The manager constructs an available
engine through a registered factory. Loading, stepping, state access and dynamic
calculations have distinct contracts. This is a source-code observation at a
pinned revision, not proof that every method works for every model or installed
backend \cite{UpstreamPlatformReview}.

Ask three separate questions: does the upstream engine offer an operation;
does the wrapper implement it with the required conventions; and has that
model-operation pair been tested? An activation-driven muscle environment cannot
automatically answer an inverse-dynamics request for joint torques. A missing
capability must give an explicit unsupported result, rather than a plausible
array of zeros interpreted as physics.

\subsection{What the Engine Names Mean}

MuJoCo supplies multibody dynamics, actuators and soft contact. Drake provides
multibody modeling and tools used in control and optimization; its contact
configuration matters. Pinocchio supplies rigid-body algorithms, including
recursive Newton--Euler inverse dynamics (RNEA) and articulated-body forward
dynamics (ABA). RNEA evaluates required forces from specified accelerations;
ABA evaluates accelerations from specified forces. Tree-recursion complexity
does not establish a real-time deadline for an entire application
\cite{MuJoCoComputationReview,PinocchioAlgorithmsReview,DrakeHydroelasticReview}.

OpenSim represents musculoskeletal models and force components. MyoSuite is a
collection of muscle-driven environments built on MuJoCo, not an OpenSim runtime;
the provenance of a converted model differs from its current simulation backend
\cite{OpenSimHuntCrossleyReview,MyoSuitePlatformReview}. Choose an engine by
required joints, forces, contacts, derivatives and available validation.
A universal ranking such as ``most accurate'' or ``best for golf'' is not
justified by this feature list.

\section{State, Force and Time Contracts}

Write the mechanical state as $(q,v)$, with
\begin{equation}
 \dot q=N(q)v,\qquad M(q)\dot v+c(q,v)
 =\tau_{\mathrm{act}}+\tau_{\mathrm{pass}}+J(q)^T\lambda.
\end{equation}
Here $c$ includes selected inertial and gravitational bias terms; passive forces
must not also be counted in $c$ if they appear on the right. A wrapper must
declare what its ``bias'' output includes. Configurations and generalized
velocities need not have equal array sizes: a unit quaternion has four stored
components but describes three rotational degrees of freedom. Its derivative
is not the angular-velocity vector \cite{MuJoCoComputationReview}.

The command $u$ may denote joint torque, desired position, actuator input or
muscle excitation. Activation and contraction dynamics can add state before
force reaches the skeleton. Setting $u=0$ is therefore not generally the same
intervention as setting generalized torque to zero. Specify force frames, signs,
units, timestamps and command holding rules before comparing a measured swing,
a synthetic motion and a simulated release.

\section{A Fully Specified Pendulum}

Consider a uniform solid cylinder of mass $m$, length $L$ and radius $r$, hinged
at an end about an axis perpendicular to its length. Its COM is $L/2$ from the
pivot. The transverse COM and hinge inertias are
\begin{equation}
 I_C=\frac{m(L^2+3r^2)}{12},\qquad
 I_P=I_C+m(L/2)^2=m\left(\frac{L^2}{3}+\frac{r^2}{4}\right).
\end{equation}
The thin-rod limit is $mL^2/3$ about the pivot; a point bob at distance $L$
would instead give $mL^2$. These describe different mass distributions.
Let $q=0$ point vertically downward, positive rotation be about world $+y$,
and gravity be world $-z$. With viscous hinge damping $b\geq0$,
\begin{align}
 I_P\ddot q+b\dot q+mg(L/2)\sin q&=0,\\
 E&=\tfrac12 I_P\dot q^2+mg(L/2)(1-\cos q),\\
 \dot E&=-b\dot q^2.
\end{align}
Damping has units N\,m\,s/rad; energy is in joules. Defining
$W_d(t)=\int_0^t b\dot q^2\,ds$ gives the exact identity
$E(t)+W_d(t)-E(0)=0$. This is a numerical residual without dividing by $E(0)$,
which is zero at rest in the downward configuration.

\begin{lstlisting}[language=Python, caption={Cylinder Pendulum with Explicit Energy Accounting}]
from dataclasses import dataclass

import numpy as np
from scipy.integrate import solve_ivp

GRAVITY = 9.81  # m/s^2; a declared example parameter


@dataclass(frozen=True)
class RodParameters:
    """Positive solid-cylinder parameters; damping is nonnegative."""

    mass: float = 1.0
    length: float = 1.0
    radius: float = 0.02
    damping: float = 0.05

    def __post_init__(self) -> None:
        """Reject nonphysical parameters before constructing dynamics."""
        values = np.array([self.mass, self.length,
                           self.radius, self.damping])
        if not np.all(np.isfinite(values)):
            raise ValueError("parameters must be finite")
        if np.any(values[:3] <= 0) or self.damping < 0:
            raise ValueError("positive mass/dimensions; damping >= 0")

    @property
    def pivot_inertia(self) -> float:
        """Transverse hinge inertia in kg m^2."""
        return self.mass * (self.length**2 / 3 + self.radius**2 / 4)


def simulate_pendulum(parameters: RodParameters,
                      initial: tuple[float, float],
                      times: np.ndarray) -> dict[str, np.ndarray]:
    """Integrate (angle, rate, dissipated work) on a requested output grid."""
    times = np.asarray(times, dtype=float)
    state = np.asarray(initial, dtype=float)
    if (times.ndim != 1 or times.size < 2
            or not np.all(np.isfinite(times))):
        raise ValueError("times must be a finite 1D grid with >= 2 samples")
    if times[0] != 0 or np.any(np.diff(times) <= 0):
        raise ValueError("times must start at zero and strictly increase")
    if state.shape != (2,) or not np.all(np.isfinite(state)):
        raise ValueError("initial must contain finite angle and rate")
    inertia = parameters.pivot_inertia
    gravity_moment = parameters.mass * GRAVITY * parameters.length / 2

    def derivative(time: float, values: np.ndarray) -> list[float]:
        """Mechanical flow and cumulative dissipated work."""
        angle, rate, _ = values
        torque = -parameters.damping * rate - gravity_moment * np.sin(angle)
        return [rate, torque / inertia, parameters.damping * rate**2]

    solution = solve_ivp(
        derivative, (0.0, times[-1]), [*state, 0.0], t_eval=times,
        method="DOP853", rtol=1e-10, atol=1e-12,
    )
    if not solution.success:
        raise RuntimeError("pendulum integration failed")
    angle, rate, dissipated = solution.y
    energy = 0.5 * inertia * rate**2 + gravity_moment * (1 - np.cos(angle))
    return {"t": times, "q": angle, "qd": rate,
            "energy": energy, "dissipated": dissipated}
\end{lstlisting}

For an example call, use the default parameters, initial state $(0.4,0)$,
and 121 equally spaced output times from zero to three seconds.
Energy includes the initial sample. This uses
SciPy directly and does not invoke an UpstreamDrift adapter. Requested sample
spacing is not the adaptive integrator's internal step size. Check tolerance
refinement and the energy-work residual; neither an energy check alone nor
agreement with this idealized model validates human segment parameters.

\section{Connecting the Example to the Swing}

Segment inertia determines how torque changes angular acceleration; the
configuration-dependent Jacobian maps motion to clubhead velocity. Damping
dissipates energy, while constraints can redirect motion without supplying an
independent energy source. Feedback changes future commands and the trajectory
on which these quantities are evaluated. To study one contribution, preserve
the remaining model and intervention assumptions explicitly.
Chapter~\ref{ch:building-models} encodes this pendulum as a model file;
Chapter~\ref{ch:engine-comparison} explains comparisons that distinguish a
different physical model from a different numerical method.

\section*{Exercises}
\begin{enumerate}
 \item \textbf{Energy and Work.} Evaluate $E+W_d-E(0)$ for damped and undamped
 motion. Tighten solver tolerances. Explain why decreasing $E$ alone is not an
 integration-error measure when $b>0$.
 \item \textbf{Linear Limit.} Derive $\omega_0=\sqrt{mgL/(2I_P)}$ for small
 angles. Compare with decreasing initial displacement and separate
 linearization error from numerical error.
 \item \textbf{Integrator Choice.} Implement semi-implicit Euler, which updates
 velocity before position, and compare with a higher-order method using phase
 and work-balance errors. Do not infer exact energy conservation from the word
 ``symplectic.''
 \item \textbf{Adding a Link.} Declare the second link's COM and inertia before
 deriving coupled dynamics. Investigate sensitivity to initial conditions for
 the chosen regime; a double pendulum is not chaotic on every trajectory.
\end{enumerate}
